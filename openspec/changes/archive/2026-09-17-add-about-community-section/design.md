## Context

`src/pages/about.astro` already has two full-bleed bands (`.skills-band`, `.ai-band`) that break out of the centered `.about` column to `100vw` via negative margins, then re-cap their inner content at the same 90rem width the rest of the page uses. See `about.astro:566-610`. This change reuses that pattern for the new closing section so its background circles can bleed to the true viewport edge, as required by the spec's "flush with the viewport edge" wording — not just the content column edge.

`tokens.css` documents the site's color system as grayscale-only ("hierarchy comes from hairlines, spacing and type, never from color-blocking"). This change is the first to introduce literal color values (`#FFF4E4`, `#FFFDE5`) and a decorative `filter: blur()` shape. See proposal.md - Why.

## Goals / Non-Goals

**Goals:**
- Reuse the existing full-bleed band pattern rather than inventing a new bleed mechanism.
- Reuse the existing zero-gap grid technique already used by `.skills` at its 4-column breakpoint (`about.astro:967-970`) for the two side-by-side cards, so per-card padding does the spacing work instead of `gap`.
- Keep the color/blur usage scoped to this one section only.

**Non-Goals:**
- No change to `tokens.css` or any shared component — the color values are local to this section's `<style>` block, not promoted to tokens.
- No reuse/adaptation of the home page's `.side-project` card chrome (border/shadow) — this section's cards are intentionally bare (image + caption only), per proposal.

## Decisions

**Full-bleed band, not a contained section.** The section uses `100vw` + `margin-left/right: calc(50% - 50vw)` (matching `.skills-band`/`.ai-band`) so the two background circles can be positioned relative to the true viewport edges via `position: absolute` inside it. The heading + cards live in an inner wrapper capped at the same `calc(90rem - (page-padding-inline * 2))` width used by `.skills-band-inner`/`.ai-band-inner`, keeping their edges flush with the rest of the page's content.

**Circles are decorative, non-interactive absolutely-positioned spans anchored to the cards row, not the section box.** Two `<span aria-hidden="true">` elements live inside `.community-cards` (which gets `position: relative`), each a large circle (`border-radius: 50%`, 600px, `filter: blur(600px)`) positioned `top: 50%` with `transform: translateY(-50%)` (vertically centers them on the cards row regardless of heading height) and `left: 0` / `right: 0` with a matching horizontal `translateX` (sits them just outside the left/right edge of the two-column grid, i.e. beside the cards rather than at the section's corners). `pointer-events: none` keeps them non-interactive.

**Bleed-without-clipping wrapper.** `.community-band` alone doesn't clip its own overflow, which would let the glow (and the horizontal overflow from its width) leak past the viewport edge and risk a horizontal scrollbar. Wrapping only `.community-band` (not 工作經歷) in `.community-band-clip` solves both directions at once:
- `width: 100vw` + `overflow: hidden` gives horizontal containment (same technique already proven for `.skills-band`/`.ai-band`, scoped locally here instead of leaning on the global `html { overflow-x: hidden }`).
- `margin-top: -560px; padding-top: 560px;` is a paired trick: the negative margin pulls the wrapper's box 560px higher (visually overlapping the tail of 工作經歷 above it), while the equal padding-top pushes the actual `.community-band` content back down by the same amount — net effect, `.community-band`'s visible position is unchanged, but the wrapper's own clipping box now extends 560px above it. Anything the glow paints within that extended region (i.e. bleeding into 工作經歷) is not clipped; anything trying to go past the wrapper's *bottom* edge (unextended — exactly `.community-band`'s own bottom, right where the Footer starts) is clipped. This is what satisfies "bleeds into the section above, not into the Footer" without touching 工作經歷's own markup/CSS at all.
- `.community-band-clip` also carries `position: relative; z-index: -1`, which — per standard CSS stacking order — paints the whole wrapper (glow + community-band content) *behind* 工作經歷's normal (static, non-positioned) content in the region where their boxes now overlap. Without this, the later-in-DOM wrapper would paint on top of 工作經歷's tail content instead of behind it. Elsewhere (the community band's own unique space at the bottom of the page, where nothing else occupies the same pixels), the negative z-index has no visible effect — the content renders normally.

**Two-column grid with an 80px column gap.** Desktop layout uses `display: grid; grid-template-columns: repeat(2, 1fr); gap: 0 80px;` for the two card containers, with horizontal centering and the 24px image-caption gap applied inside each card via its own flex column. Mobile switches the grid to a single column, with the 12px image-caption gap applied per-card the same way.

**Heading needs its own stacking order above the glow-carrying cards row.** `.community-cards` is a positioned element (`position: relative; z-index: 0`, needed so its own `z-index: -1` glow children stay behind its `<li>` cards). A positioned element paints above static in-flow siblings by default, regardless of DOM order — so without a fix, `.community-cards` (carrying the glow) would paint *over* the plain-static `.section-heading` sibling above it wherever the glow's vertical reach overlapped the heading, even though the glow's own internal z-index is negative (that negative value is only relative to `.community-cards`' own stacking context, not the heading's). The fix: give `.community-band-inner .section-heading` `position: relative; z-index: 1` — now both are positioned, explicit z-index compares directly (1 > 0), and the heading correctly paints above the cards-row (and the glow it carries) in the overlap region.

**Images stay proportional via `max-width`/`max-height` on an auto-sized image.** Each image renders with `width: auto; height: auto; max-width: 100%; max-height: 468px` (0.9× the original 520px cap) — the browser's standard replaced-element sizing algorithm satisfies both constraints simultaneously without distortion or cropping, so `object-fit` isn't needed. The `<Image>` component's own `width`/`quality` props (1200 / 90) are unrelated to this display cap — they control the resolution of the generated source file, kept generous so the display-size reduction doesn't cost any sharpness.

**Section heading reuses `.section-heading`/`.section-icon`/`.section-rule` verbatim** (same classes already used by 我擅長的事/工作經歷), for visual consistency with the rest of the page.

**Footer's own `margin-top` is overridden to 0 on this page.** `Footer.astro` has a global `.footer { margin-top: calc(var(--space-7) + var(--space-4)) }` (144px), meant for pages whose last section has no bottom padding of its own. Since this section already ends in 160px of `padding-bottom`, stacking Footer's own margin on top of that would produce a much larger gap than the spec's "no gap beyond the section's own padding." `about.astro` overrides it with `:global(footer.footer) { margin-top: 0 !important; }`, scoped to this page only (the rule only exists in this page's compiled stylesheet); `!important` is needed because Astro's scoped `[data-astro-cid-*]` attribute selector on Footer's own rule outranks an unscoped selector of otherwise-equal shape.

**`.about`'s own trailing bottom padding is also zeroed.** `.about { padding-block: clamp(1.5rem, 4vw, 2rem) clamp(3rem, 6vw, 4.5rem); }` pre-dates this change and was sized for whatever section used to end the page. With `.community-band-clip` now always the last child and providing its own generous 160px `padding-bottom`, that trailing value (up to 72px) was pure extra gap stacked on top of the section's own padding — changed to `padding-block: clamp(1.5rem, 4vw, 2rem) 0`.

**Two entrances stagger via `transition-delay`, not two separate observers.** Each `.community-card` gets the shared `reveal` class (observed independently by BaseLayout's IntersectionObserver, same mechanism as `.experience-item.reveal`), plus `.community-card.reveal { transform: translateY(2rem); transition: opacity 500ms ease-in-out, transform 500ms ease-in-out; }`. Because the two cards sit at nearly the same scroll position (side by side on desktop, close together on mobile), they'd otherwise become `.is-visible` in the same frame; `:nth-of-type(1)` / `:nth-of-type(2)` add `transition-delay: 0ms` / `180ms` (mirroring `.skill:nth-child`'s existing stagger pattern) so the second card visibly follows the first rather than both fading in at once. `:nth-of-type` (not `:nth-child`) is required because the two `.community-glow` `<span>`s are earlier siblings within `.community-cards` and would otherwise throw off a plain child-index count.

## Risks / Trade-offs

- **Design-language departure** (color + blur where the rest of the site is strictly grayscale/hairline-based) → Mitigated by scoping the colors to this section's own `<style>` block only, not adding them as reusable tokens, and calling out the departure explicitly in the proposal so it's a recorded decision rather than an unreviewed drift.
- **Full-bleed circles + `filter: blur()` can be expensive to repaint on some mobile GPUs if not layered correctly** → Mitigate by keeping the circles as simple absolutely-positioned solid-color shapes (not gradients or SVG filters) and blurring the whole element once, not per-frame.
