# 作品集 Case Study 撰寫 Skill

面向 UIUX 設計師求職作品集的 Case Study 撰寫與優化指引。核心原則：**所有內容以展示設計師的價值為核心，而不只是陳述事實。**

---

## 一、Case Study 標準架構

每份 Case Study 依序包含以下節：

```
引言（一句話，無節標題）
01｜專案背景
02｜研究洞察（節標題依案例自訂）
03｜設計決策
04｜成果
05｜反思
```

### 各節功能說明

**引言**
- 不加節標題，直接放在基本資訊和保密說明之後
- 一句話說清楚：產品目的 + 設計師的任務
- 格式：`[產品/系統一句話描述]，我負責[設計師的具體工作]，讓[使用者/業主]能[達到什麼效果]。`
- 不做背景鋪陳，背景留給 01 節

**01｜專案背景**
- 說明系統/產品是什麼、服務誰、在什麼情境下被使用
- 重點：讓讀者感受到「這個問題為什麼值得被設計」
- 說清楚設計師的角色與責任範疇
- 避免與引言重複

**02｜研究洞察**
- 節標題依案例自訂，應帶有觀點（例：「需求的轉譯者——從訪談記錄到設計決策」）
- 說明設計工作的核心難點在哪、發現了什麼
- 必須包含 **Key Insight** callout block，格式：
  ```
  > **Key Insight**
  > [一到兩行，說明最重要的洞察，不用人稱代名詞]
  ```
- Key Insight 要說的是「這件事為什麼難、為什麼需要判斷」，不是工作描述

**03｜設計決策**
- 每個決策依序包含：問題情境 → 設計判斷 → 解法 → 截圖標注
- 決策數量：3–4 個為佳
- 截圖標注緊接在對應解法段落之後，不集中放在文末
- 截圖標注格式：`*（截圖：[具體說明這張圖展示什麼、對比什麼]）*`

**04｜成果**
- 先說「怎麼交的」，再說「交了什麼」
- 用過程指標取代難以取得的數字成果（例：頁數、模組數、覆蓋行為數、訪談場次、待確認事項數）
- 避免只列清單；每個指標要帶一句說明它代表什麼

**05｜反思**
- 聚焦一個具體事件或決策過程，說明初版判斷 → 遇到什麼 → 怎麼回應
- 以**粗體引言句**收尾，這句話就是整個 Case Study 的最後一行
- 粗體句之後不再接補充說明
- 格式：`**[一句有個人立場的結論，說明這件事讓設計師確認了什麼。]**`

## 二、設計決策標題的寫法

標題應呈現「動作 + 效果/原則」的張力，讓讀者在看內文之前就能感受到判斷的存在。

**好的標題格式：**
- `[把 X 移出 Y]，[降低/縮減 Z]`
- `[順應 X]，[在 Y 裡補回 Z]`
- `[以 X 取代 Y]，保留 Z 的可見性`

**避免的標題格式：**
- 純描述解法：「統一查詢介面，以按鈕意圖區分兩階段操作邏輯」→ 說的是做了什麼，沒有說判斷
- 過於抽象：「優化使用者體驗」、「改善資訊架構」

## 三、文案編排原則

### 圖文穿插
- 截圖緊接在對應決策的解法段落之後
- 不設獨立的「設計展示」節集中放圖
- 每張截圖附 caption，說明展示什麼、對比什麼

### 敘事語氣
- 第一人稱，直接說「我判斷⋯⋯」「我將⋯⋯」「我主動⋯⋯」
- 說明設計判斷時，要說清楚：為什麼這樣做（而不是別的方式）
- 說明業主/利害關係人意見時，不要只說「業主要求」，要說你如何評估再決定

### 避免的寫法
- 「不 X，而是 Y」的句型（看起來像辯解）
- 過於分析性的句式（像學術報告而非對話）
- 結尾補充說明（削弱收尾力道）
- 人稱代名詞出現在 Key Insight 裡

## 四、展示設計師價值的檢查清單

每完成一份 Case Study，逐節對照以下問題：

**引言**
- [ ] 讀完一句話，能知道設計師做了什麼、為誰解決什麼問題嗎？

**背景**
- [ ] 讀完背景，能感受到「這個問題為什麼值得被設計」嗎？
- [ ] 有沒有說清楚設計師在這個專案的角色邊界？

**研究洞察**
- [ ] Key Insight 說的是洞察，還是工作描述？
- [ ] 有沒有說明「這件事為什麼需要能力、沒有對口、需要主動識別」？

**設計決策**
- [ ] 每個決策有沒有說清楚「為什麼這樣做、而不是其他方式」？
- [ ] 截圖標注有沒有說明對比什麼，而不只是描述畫面？
- [ ] 如果有業主意見不同的情境，有沒有說明你的判斷過程？

**成果**
- [ ] 成果是「展示品質和判斷密度」，還是「列清單」？
- [ ] 有沒有避免不屬於自己的成果？

**反思**
- [ ] 反思有沒有展示設計師的判斷能力，而不只是說「學到了什麼」？
- [ ] 粗體句是最後一行嗎？後面有沒有多餘的補充？

## 五、保密與事實準確性原則

- 客戶名稱以產業描述替代（例：「某大型綜合證券公司」）
- 不描述現有流程的具體問題情境（如：「每次都要打電話確認」），聚焦系統設計本身
- 不寫入無法確認的數據或效果（用過程指標替代）
- 不描述不屬於自己的工作（訪談由他人主導、成果由團隊達成等）
- 如有 NDA，在 Case Study 開頭加保密說明，格式：
  ```
  > **保密說明：** [說明匿名化範圍]。本文聚焦於設計研究方法、資訊架構決策與 UX 邏輯的呈現。如需了解更多細節，歡迎面試時進一步討論。
  ```

## 六、參考架構對照

以下為從優質作品集案例歸納的架構模式（Andy Chien / Adham Dannaway / Nelly）：

| 模式 | 說明 |
|------|------|
| 開頭一句話定義設計命題 | 所有參考案例共同做到的基本盤 |
| 截圖穿插在對應段落之後 | 圖文敘事一體，不是附件 |
| 設計決策有洞察標題 | 讓讀者在看內文前就感受到判斷 |
| Key Insight 獨立視覺化 | 把最重要的洞察從段落裡拉出來 |
| 反思以個人立場句收尾 | Adham Dannaway 的標準做法 |
| 成果先說品質再說規模 | 讓招募者先感受到判斷密度 |

## 七、適用的 Case Study 類型

此 skill 適用於：
- B2B 內部管理系統
- B2C SaaS 平台
- 金融/法規合規類系統
- 0→1 產品設計
- 功能模組設計（非完整產品）

不同類型的差異主要在 02 節（研究洞察）和 04 節（成果）的指標選擇，其餘節的結構相同。
