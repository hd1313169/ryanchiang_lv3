## 專案背景

這是一間大型證券公司的業務 CRM 系統，服務對象橫跨業務員、研究員等多種角色。首頁儀錶板、客戶查詢、行銷活動、數據報表、系統設定，五大功能模組分多個 Phase 分批交付，外部合作對象是一間大型軟體開發公司。

我以 UX/UI 設計師的身份負責全模組的設計決策與 Prototype 製作。模組數量多、週期緊湊，怎麼在這個條件下維持交付品質，是專案開始就得想清楚的問題，不是進行到一半才能臨時應對的事。

| 痛點 | 設計挑戰 | 我的任務 |
|------|---------|---------|
| 系統模組多、週期緊湊，缺乏一套可快速交付、有效溝通且支援持續迭代的Prototype 方法。 | 在既有 Figma Prototype 交付慣例下推動流程改變，同時建立一套可標準化、可複用的 AI 工作流。 | 建立一套可複用的 AI Prototype 工作流，讓內部 PM、外部開發團隊、業主都能直接操作 Prototype，以操作取代說明。 |

## 設計挑戰

### 數據報表的互動複雜度，突破了工具的結構性限制

Phase 1 靜態設計稿定稿後，動態交付時間只剩兩天。報表模組的互動需求攤開來看：縱向三層 drill down 展開、橫向年份展開月份再展開週次、頂端欄位凍結、左側欄位凍結。四個維度，要在同一個介面同時展示、同時運作。

Figma Prototype 在這裡碰到的不是複雜度問題，而是結構性限制。它可以模擬單一互動路徑，但撐不住多維度同時運作的操作狀態。這個差距，在一般畫面裡或許還能靠口頭補充帶過——但這套系統的溝通對象有三方：內部 PM、外部開發團隊、業主。三方都需要親自在 Prototype 上感受系統行為。用靜態稿解釋報表邏輯，每次 review 都得設計師坐在旁邊補說明，這個成本不是一次，是整個專案裡反覆出現的摩擦。

還有一層限制更根本。部分利害關係人不擅長操作 Figma，也沒有意願學。每次要看 Prototype，得另外約一場會議現場 demo，會後還得補一份說明文件讓對方回去對照。走一次流程，溝通成本就疊了兩層。

兩天的時限讓判斷變得清晰：繼續用原有框架撐完，或者換一條路。

> **關鍵洞察**
>
> Figma Prototype 的限制不在工具本身，在於它的互動模型與複雜業務系統的操作邏輯之間存在結構性落差。當溝通對象需要「操作」而非「觀看」，這個落差就會轉化成三方對齊的摩擦成本。

## 設計決策

### 先把整套流程自己跑通，再去提案

提案之前，我先替自己設了一個條件：不做半套。要說服別人改變原有的交付方式，光說明工具能做什麼遠遠不夠。得先確定這套流程從頭到尾都能跑，產出要禁得起檢驗，才有資格去談。

於是我把一個完整模組的製作成本，全部攬到自己身上。工具怎麼分工、哪個環節該由誰做，這些判斷得先在實際操作中摸清楚。

整套工作流以 <img class="inline-logo" src="/images/case-05/logo-claude.png" alt="" />**Claude Code** 為核心執行環境。透過 <img class="inline-logo" src="/images/case-05/logo-figma.png" alt="" />**Figma MCP** 在 Claude Code 和 Figma 之間建立橋接，直接讀取 Design System 中的元件定義，把下拉選單、Date Picker、Table Cell 這些使用頻率較高的元件轉成 Prototype 的共用元件庫，確保畫面精度能對齊設計稿。規格轉換的部分則透過 <img class="inline-logo" src="/images/case-05/logo-openspec.png" alt="" />**Superpowers**，以 SDD（規格驅動開發）的方式，在 Claude Code 內將規格文件直接產出可互動的前端框架，互動邏輯有明確的規範，讓 AI 不會自己瞎猜亂做。

### 以 Token 架構確保設計稿與 Prototype 的一致性

Prototype 要能被信任，前提是它的畫面必須和設計稿對得起來。多模組、多頁面的系統若直接用硬編碼顏色和間距，改一次需求就得逐頁修正，這個成本在快速迭代的專案裡根本撐不住。

我判斷需要以 token 化的方式建立設計系統的單一來源：所有顏色、字級、間距統一定義在 `tokens.json`，由 AI 實作 build 流程，讓每一頁畫面從同一份 JSON 計算出來，而不是各自維護。Token 結構裡保留了 `figma` 欄位，每一個 token 都能回溯到設計稿中對應的變數，設計稿仍然是視覺的唯一真相，Prototype 是它加上行為的可執行版本。

這個架構讓需求調整從「逐頁修改」變成「改一處、全站生效」，也確保多個 Phase 迭代下來，Prototype 的畫面精度始終和設計稿保持一致。

工具負責產出，但哪個環節該交出去、哪個環節不能放手，是我自己劃的線。這條界線劃在哪裡，決定了後面拿出去的東西能不能被信任。

## 心得與反思

對我來說，最困難的不是流程設計，而是面對經驗和資源都更加豐富的外部團隊與業主，要不要打破慣例提出自己的解決方案的不確定感。我一貫的做法都是先驗證概念可行，再拿證據去說服、影響他人。AI 只是加速了整個解決方案實踐的流程。

**在複雜的協作環境裡，說服需要的不是論述，而是讓人可以親自操作的東西。**

最意外的問題是在 Prototype 交付之後才浮現出來。由於 Prototype 擬真程度太高，合作團隊和業主更容易放大檢視細節，出現「這個功能應該要可以操作」、「這個欄位的加總值不對」等問題，導致後續的調整方向從「是否符合使用體驗」，偏移到功能完整性與資料的補齊。除了學習工具的使用以外，當能做到的事越多，我們就越需要定義清楚哪些事是真的該做的。

> **關鍵洞察**
>
> 高保真 Prototype 能以假亂真是優點，但當使用者無法區分「模擬互動」和「真實功能」時，驗證目標就會被稀釋。Prototype 的邊界不只需要在製作前定義，更需要在交付後反覆釐清。
